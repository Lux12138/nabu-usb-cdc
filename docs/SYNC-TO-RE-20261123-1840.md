### 2.1.1 两个"丢包"不是一回事（我们一开始也说错了，这里更正）

| 计数器 | 值 | 含义 |
|---|---|---|
| `STATUS rxo` = `dwc3_rx_overflow()` | **0** | **控制请求**的 RX 环没有溢出 —— 13 条命令零丢失 |
| `QCOM USB LOSS overflow=` | **0** | 日志环形缓冲**容量**没写满 |
| **`QCOM USB LOSS contention=`** | **7577** | **生产者撞上 `busy` 直接丢弃的字节数**（`QcomUsbBuffer.h:29-32`）|

`dropped = overflow + contended`（`QcomUsbBuffer.h:73-77`），所以 **`contention` 是真丢字节**，
不是"重试计数"。全轮 65 条 LOSS 记录，末条 `contention=7577`，
相对 5,014,855 B 的接收量 = **0.151%**。

**⇒ 结论要改口径：控制通道零丢失；日志文本约 0.15% 被丢弃**（表现为偶发断行），
这不影响 `NABULOG1` 落盘（落盘是独立内存环形缓冲），也**不影响任何 verb 回复**。
（CDC 吞吐模型仍然是 p50 ≈ 4 KB/s，本轮实测 5.8 KB/s 属于上限附近，竞争就发生在这里。）

**同期 UFS 读在推进。** 两个计数器的确切语义（我们核过源码，**不要误读**）：

| 字段 | 真源 | 真实含义 |

| `rd` | `NativeUfs.cpp:3044-3047` + `RootWindowRead.h:53` | **窗口 copy 迭代次数**，**不是块数**（`ops.copy()` 每次 while 迭代只调一次）|

**逐进程配对（`backboardd`，pid 56）：**

| 时刻 | `t` | `rt` | `rd`（迭代数）|
|---|---|---|---|
| spawn 开始 | 92.19 s | 14.20 s | 39,650 |

**【推断，不是实证】** `rt` 是全局累计值，**不能百分之百算在 `backboardd` 自己头上**
（同期别的线程也可能在读）。但两点支持"排队"这个解释：
① 这段时间内 `rd` 涨了 10.8 万次迭代，说明读通道**确实在满负荷跑**；
② 读路径只有**一把** `windowLock`（`RootWindowRead.h:29`，有界等待、串行进入），

**这个瓶颈是可定位的**：根卷按需分页把 17 个服务串成一队。
**请贵方从代码侧看两件事**：能不能让首启的页读**并行**（我们只有一把 `windowLock`），

### 3.2 T50 §7.2 `kern.kdbg.*` 不持锁读法 —— 打通并读到真值 ✅

```
KDBG OK enabled=0 mode=0 live_flags=0x00000000 kdc_flags=0x00000001 cpus=40
        oldest_time=0x000000002fcfa247
```

**做法照贵方给的**：直接读导出的 `kd_control_trace`（锁是 `lck_spin`，不睡眠）。

**但偏移不能手算** —— 我们第一版按 `struct kd_control` 镜像算成 `+0x38`，
读到的是 `kdc_storage_used` 的低半（kb-69 的 `0x37e36c38` 是假值）。
**改用链接后内核反汇编里编译器自己的偏移**：

```
+0x08  enabled:1, mode:3
+0x1c  kdebug_cpus
+0x24  kdc_flags
+0x2c  kdc_live_flags
+0x30  kdc_oldest_time     ← 不是 +0x38
```

根因：`union kds_ptr` 是 **21+11 位域 over `uint32_t`（4 字节）**，不是指针。

## 5. 没做的 / 为什么

| 项 | 结论 | 依据 |
|---|---|---|
| **T48 ① kdebug 事件镜像进 ring** | **建议不做** | `kd_buffer_trace` 未导出；`kdbg_dump_trace_to_file` 内部 `ktrace_lock` 是 **mutex**（会冻 CDC）+ 走 VFS。要做得改 XNU，碰的是 CDC 生命线 |
| **只开 `trace_panic=1`** | **不可行** | 落 `/var/log/panic.trace` = Data 卷 **APFS**，我们只有 `READ`/`READPA`/`READUFS`，没有 APFS 通道 |
| **原生 panic stackshot** | **arm64 死路** | `panic_stackshot_to_disk_enabled()` 恒 FALSE 且**无调用者**；`panic_stackshot_buf` 是 x86-only |
| **`gPanicBase`（方案 A）** | **已证伪** | `0x9b000000` 无后备物理页，两轮实证（panic / 卡死）|
| **panic → KDP 继续运行 / 软件复位** | **不改 XNU 不可行** | 返回条件要 `DBOP_DEBUGGER`（panic 是 `DBOP_PANIC`）；`serial_pending` 在 `!armed` 时直接 return 0。两次修复都失败：drain 撞 `usb_busy` 自锁；无锁版破坏 TRB 环导致 panic 完全静默。**代码已回滚，注释保留失败记录** |

**我们没有主动触发 panic 去测 KDP 退出** —— 那是拿设备冒险换不需要的功能，
panic 通道的用途是**读日志**，不是撞它。

### 7.1 上板纪律（如果贵方也要动设备，这三条别踩）

1. **一个 boot 只能 open 一次 CDC。** `close()` 后再次 `open()` 要么阻塞 ~120 s、
   要么 `ERROR_GEN_FAILURE(31)` / `PermissionError(13)`，**只有断电复位能恢复**。
   换工具 = 破坏性操作。
2. **命令文件只用 `>>` 追加，绝不截断。** 控制台按**字节偏移**追踪读到哪里，
   截断后 `size > pos` 不成立，新命令会被**静默跳过**（实测：`read 0x… 4` 被读成 `4`）。
3. **复位一律手动发。** 我们不挂自动复位兜底 —— 它会在该看日志的时候把设备抢走。

**WDT 咬回的判据只有一个**：**COM3 消失 AND `adb devices` 出现 `recovery`**。
`adb devices` 为空**不等于**设备死了（系统态 adb 本来就不上线）。
